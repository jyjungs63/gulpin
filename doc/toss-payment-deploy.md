# 토스페이먼츠 연동과 보안 점검

## 결제 흐름

- 쇼핑몰은 장바구니를 저장한 뒤 카드 결제를 시작한다. 같은 주문 저장 요청을 재시도하면 기존 주문번호를 반환한다. 결제창을 닫거나 승인이 지연되면 주문 내역에서 해당 주문을 다시 열 수 있다.
- 교재 주문은 구매내역서를 저장한 직후 또는 주문 내역에서 카드 결제를 시작한다. 본사 관리자는 두 화면에서 카드 전액 환불을 처리하고 구매자는 토스 영수증을 조회할 수 있다.
- 교재 주문 금액은 저장 시 서버 가격표로 계산해 `pg_amount`에 보관한다. 적용 전 교재 주문은 현재 가격표로 기존 주문서를 재검증한다. 쇼핑몰은 DB의 상품 가격과 배송비로 합계를 계산한다.
- 토스 승인 요청 전에 주문의 소유자, 상태, 금액과 결제 복귀 토큰을 확인한다. 승인·취소에 결제별 멱등키를 사용한다. 토스 응답의 상점 ID, 결제번호, 결제 키, 통화, 결제 및 잔액 금액을 확인한 뒤 PG 거래와 주문 상태를 한 트랜잭션에 저장한다. 응답을 잃어버린 거래는 동일 결제를 조회하고 재시도한다.
- 토스 웹훅의 서명과 전송 시간을 검증하고, 토스 API에서 조회한 거래를 반영한다. 토스 콘솔에서 부분 환불을 진행하면 거래를 부분 환불 상태로 기록한다. Gulpin 화면은 최초 금액의 전액 환불을 지원한다. 부분 환불 이후 잔액 환불은 토스 콘솔에서 처리한다.

## 환경 설정과 배포

1. 토스 개발자센터에서 같은 상점과 모드의 **API 개별 연동 키** 및 상점 ID를 확인한다. 카드/간편결제 통합결제창의 `test_ck_`·`test_sk_` 또는 `live_ck_`·`live_sk_` 조합을 사용한다. 운영 상점에서 이 결제창으로 사용할 결제수단이 활성화됐는지 확인한다. [토스 결제창 연동 가이드](https://docs.tosspayments.com/guides/v2/payment-window/integration)
2. 작업본을 배포하기 전에 DB를 백업한다. 테스트와 운영 DB를 분리한다. MariaDB 쇼핑몰과 교재 주문의 운영 DB에는 `gulpin_porlist`, `shopping_orders`, `gulpin_payments`가 InnoDB인지 확인한다. 앱 초기화는 기존 데이터에 컬럼과 테이블을 추가하므로 초기 실행 계정에 필요한 DDL 권한을 주거나 DBA가 같은 DDL을 사전에 적용한다. SQLite는 교재 주문을 지원한다.
3. PHP 환경변수 또는 Git이 무시하는 `_private/.env`에 설정한다. 운영 호스트는 `GP_DB_ENV=production`으로 설정한다. 기존에 SQLite를 운영한다면 SQLite 서비스에서만 `GP_ENABLE_SQLITE=1`을 설정하고 DB 파일을 문서 루트 밖에 둔다.

```dotenv
TOSS_CLIENT_KEY=test_ck_발급값
TOSS_SECRET_KEY=test_sk_발급값
TOSS_MERCHANT_ID=상점ID
TOSS_WEBHOOK_SECRET=개발자센터의_웹훅_보안키
GP_PASSWORD_VIEW_ENABLED=0
```

4. PG 운영 전 관리자 확인용 비밀번호 사본 삭제와 키 폐기를 적용한다. 기존 계정의 로그인 해시는 그대로 유지된다. [비밀번호 확인 기능 종료 절차](password-view-deploy.md#pg-도입-시-종료)
5. 개발자센터에서 `PAYMENT_STATUS_CHANGED`를 사이트의 HTTPS `/payment/webhook.php`에 등록한다. SQLite 교재 주문 환경에서 수신기를 검증할 때는 `TOSS_WEBHOOK_DB=sqlite`를 서버에 설정한다. 웹 서버와 프록시에서 토스 서명 및 시간 헤더를 전달하고 서버 시각을 동기화한다. [토스 웹훅 설정](https://docs.tosspayments.com/guides/v2/webhook), [토스 웹훅 이벤트](https://docs.tosspayments.com/reference/using-api/webhook-events)
6. Apache의 파일 차단 설정을 적용한다. 다른 웹 서버에서는 동등한 차단 규칙을 적용한다. 사이트 전체를 HTTPS로 운영하고 브라우저가 접근하는 토스 복귀 URL의 쿼리 문자열이 로그에 남지 않도록 설정한다. TLS를 앞단 프록시에서 종료한다면, 외부 헤더를 제거하고 프록시가 `X-Forwarded-Proto: https`를 설정하는 구성에서만 `GP_TRUST_TLS_PROXY=1`을 사용한다.
7. 테스트 키로 쇼핑몰·교재 주문 각각 결제, 사용자 취소, 승인 화면 재진입, 본사 전액 환불, 토스 콘솔 환불 웹훅을 확인한다. 토스 개발자센터 금액과 주문 내역을 대조한다. 검증 이후 운영 상점과 운영 키를 설정한다.

로컬 회귀 테스트는 `php tests/payment-policy.php`로 실행한다. 운영 DB에서 실행하면 안 된다.

## 장애 시 거래 확인

- `CONFIRMING`이면 고객 주문 내역의 승인 상태 확인으로 재조회한다. `CANCELING`이면 본사에서 같은 주문의 환불 상태를 확인한다. 통신이 끊겨도 토스가 승인 또는 취소를 완료했을 수 있다.
- 기존 초안에서 PG 승인과 주문 DB 저장 중 하나만 끝난 거래는 개발자센터의 거래번호와 주문번호를 대조한다. 주문이나 결제 상태를 SQL로 먼저 변경하면 실제 거래와 어긋날 수 있다.
- 토스 API는 동일 멱등키를 15일간 기억한다. 오래된 미확정 건은 개발자센터에서 거래 상태를 확인한다. [토스 멱등키 헤더](https://docs.tosspayments.com/reference/using-api/authorization#멱등키-헤더)

## 보안 점검 결과

| 중요도 | 확인 사항 | 조치 |
| --- | --- | --- |
| 높음 | 기존 비밀번호 찾기가 아이디와 연락처 정보만으로 비밀번호를 응답했다. 관리자용 확인 사본도 활성화돼 있었다. | 공개 복구를 담당자 재설정 안내로 바꾸고 관리자용 확인 사본 생성을 기본값에서 비활성화했다. 운영 DB의 사본 삭제와 키 폐기는 배포 작업이다. |
| 높음 | 전자책 관리 API와 후기 수정·삭제 API에 서버 관리자 확인이 없었다. 비공개 후기 목록도 브라우저 파라미터로 조회됐다. | 현재 DB 역할이 본사인 계정에만 허용했다. 공개 후기와 전자책 뷰어는 기존 진입점에서 읽을 수 있다. |
| 높음 | SQL 덤프와 SQLite 파일이 작업 트리에 있고, Git 인덱스의 SFTP 설정에 비밀번호 값이 있다. | Apache에서 직접 접근을 차단했다. SFTP 비밀번호 교체 및 Git 인덱스·이력의 설정과 민감한 데이터 정리는 별도 작업이다. 배포에서는 덤프와 실제 DB를 웹 루트 밖에 둔다. |
| 높음 | 기존 교재 주문 PDF가 직접 URL에서 제공됐다. | 본사 또는 주문 소유자에게만 PDF를 제공하고 기존 원본 경로를 차단했다. 주문 상세 목록의 사용자 입력은 HTML에 맞춰 이스케이프한다. |
| 중간 | 전자책 폴더 검색이 임의의 파일시스템 경로를 해석하고 내부 경로를 응답했다. | 웹 콘텐츠 경로 안에서만 파일 형식을 탐색하고 실제 서버 경로를 응답에서 제거했다. |
| 추가 점검 | 학생 비밀번호를 평문으로 저장·표시하는 흐름이 학생관리 배포 문서와 소스에 남아 있다. 교재 영상 접근도 기존 주문 생성 기준이다. | 두 항목은 운영 정책과 계정 이관이 필요한 후속 과제다. |

점검은 프로젝트 소스와 배포 문서 기준이다. 운영 서버 설정, 과거 파일 접근 기록, 토스 운영 상점의 거래는 운영 환경에서 확인한다.
